02Integrations and decisions

A1HubSpot: send enquiries to your CRM Before launch

Today
The Home enquiry form and the Contact page form work: they check the visitor's details and save every message in the CMS (Inbox → Form messages). Nothing is sent to HubSpot yet.

What we will build
Each enquiry is sent to HubSpot the moment it arrives. A copy stays in the CMS so nothing is lost if HubSpot is briefly unavailable.

#Question / itemNotes
1Your HubSpot account (portal ID) and someone who can create access for usWe need a private app access token that can submit forms / create contacts. Share it through a password manager or your IT team, never by email.
2Which forms go to HubSpot?Home enquiry · Contact detailed enquiry · job applications (or elsewhere, see A3)?
3Use HubSpot forms, or create contacts directly?HubSpot forms recommended: your team sees submissions in HubSpot's reports and can add workflows without us.
4Field mapping: where each field landsName, email, phone, company, message, the "What are you looking to unlock?" choices (likely a custom HubSpot property), page sent from.
5Consent: subscription types / legal basisThe Contact form has a consent tick box ("use my details to reply"). Add an optional "send me news" tick box for marketing?
6After a submission: lead owner, status, lifecycle stage, internal alert?Usually set up as HubSpot workflows on your side.
7HubSpot tracking code on the site?It sets cookies, so it must wait for visitor consent (A4).

If no answer by launch: messages stay in the CMS inbox only, and someone must check it regularly (see A2).

A2Email alerts for new form messages Before launch

Today
Messages are saved in the CMS, but nobody is notified. A new enquiry or application is only seen if someone opens the CMS.

  1. Who receives an email for enquiries (Home, Contact) and for job applications? One address each, or a shared inbox (e.g. hello@ / careers@)?
  2. The sender address (e.g. no-reply@ your domain). Your IT team adds a few DNS records (SPF, DKIM, DMARC) so emails don't land in spam; we will send the exact records.
  3. Should visitors get an automatic confirmation email? If yes, approve the wording.

If HubSpot (A1) sends these notifications for you, we only need the job-application recipient here.

A3CV upload on job applications Recommended

Today
The Join Us form shows the CV drop zone as designed (visitors can pick a file and see its name), but the file is not sent or stored. The rest of the form works, including the LinkedIn / portfolio link.

Risk if we launch first: applicants may think their CV was sent. We can add a short note under the field, e.g. "CV uploads are coming soon: add your LinkedIn link above".

CVs are personal data: they must be stored privately (not with the public website images) and handled under UAE data protection law (and GDPR for EU applicants).

  1. CV uploads at launch, or is the LinkedIn / portfolio link enough for now?
  2. Who may download CVs: CMS admins only, or editors too?
  3. How long are CVs kept? Deleted automatically after that?
  4. Consent wording on the form (e.g. "I agree that PLG Acachet keeps my profile on file for [x] months").
  5. Should applications go to an applicant-tracking system (ATS) or HR mailbox, instead of or as well as the CMS? Which one?
  6. File rules as designed: PDF or Word, up to 10 MB?
  7. Virus scanning of uploads (small extra AWS cost)?
  8. A private storage location on your AWS account (we will specify it; part of A10).

A4Cookie consent and analytics Before launch, if any tracking is used

Today
The Cookies page shows the Manage Cookie Preferences button and a cookie table as designed; the button shows a "not connected yet" note. There is no analytics and no consent banner (the design has none). The site sets no tracking cookies, so it is compliant as it stands.

  1. Analytics wanted? Which tool (e.g. Google Analytics 4, HubSpot analytics, a cookie-free tool such as Plausible)?
  2. Which consent platform (e.g. Cookiebot, OneTrust, HubSpot's cookie banner)? It provides the banner and the panel the button opens. A banner is required as soon as any non-essential cookie (analytics, HubSpot tracking, ads) is added.
  3. Any marketing tags (LinkedIn Insight, Meta Pixel…)?
  4. The final cookie list for the Cookies page (the consent platform usually produces it from a scan).

A5Legal wording Before launch

Today
Terms & Conditions, Privacy Policy and Cookies are built with the design's outline and placeholder text, plus a notice box saying counsel must write them.

We need
Counsel-approved wording for the three documents, the "last updated" / "effective from" dates and version number. The Privacy Policy should also cover HubSpot (A1), CVs (A3) and analytics (A4) once decided. Your team can paste the text into the CMS; we can help with formatting.

A6Scheduled publishing After launch

The CMS shows a Schedule Publish option (publish a change at a set date and time). It is not switched on yet, so a scheduled change never goes live. Do you need it at launch? If yes we switch it on; if not we hide the option so nobody relies on it.

A7Who may delete content Recommended

Today editors can delete pages, case studies, team members and open roles, the same as admins. Editors can always hide sections or unpublish a page instead. Should deleting be admin-only? (We recommend yes, at least for pages.)

A8Arabic version After launch

The site is English only. Is an Arabic version planned? It affects layout (right-to-left), fonts, the CMS (each field in two languages) and web addresses, so it is best to know early even if it comes later.

A9Old website addresses Before launch, if you have a current site

If your domain has a website today, please send the list of its main addresses (or access to it). We redirect each one to the matching new page so links and Google rankings are kept.

A10Hosting approval Before launch

  • Approval of the proposed AWS setup (Middle East – UAE region).
  • An AWS account (or access to yours) and who owns billing.
  • The domain and access to its DNS.
  • Expected monthly visitors, to size the server and confirm cost.
  • Confirmation that one server is enough at launch (several need an extra shared cache; we recommend one, with automatic recovery).

A11CMS accounts Before launch

Names and email addresses of the people who will edit the site, and whether each is an Admin (everything, including users) or an Editor (content only).
